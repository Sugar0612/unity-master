## 一、预测怎么写

**为什么要先押再跑**：数字只有对着预测才变成"模型对错的信息"。B3 的教训：没押预测，"StringBuilder 比 += 慢"这种反常结果就溜过去了；押了，你会当场发现用法有错。押对=校准，押错=找到下一个要修的点，都赚。

**已跑过的（B1、B2、B5-2）→ 回忆式**：诚实重建"跑之前我以为数字是多少"，对照事实，写差距告诉我什么。示例：

```
B1
我以为：装箱 100 万次 ≈ 24MB（24B×100万）；纯 int = 0
事实：  9.6MB / 0MB
差距：  少 14MB → 中途自然 GC 扫走了一部分（= B1-Q 的答案素材）

B2
我以为：List<int> ≈ 4MB；List<object> 多一些
事实：  8.4MB / 39.6MB
差距：  漏算了数组翻倍（×2）与"引用数组+盒子"的叠加账
```

**要重跑的（B3-R/B4-R/B5-R）→ 顺序式**：先把你自己算的预测写进答题文件，再改代码开跑。可以参考量级，但**数字必须自己算**——算错了才有对照价值。

## 二、B3-R：StringBuilder 正确用法

你的错误版在循环内每次 `new StringBuilder(s)`——双份 O(n²) 拷贝所以比 += 还慢。正确骨架：

```csharp
var sb = new StringBuilder();            // 循环外 new，仅一次
long sink = 0;

GC.Collect();
long before = GC.GetTotalMemory(false);
var sw = Stopwatch.StartNew();

for (int i = 0; i < 10_000; ++i)
{
    sb.Append(i.ToString());             // 循环内只 Append（试试直接 sb.Append(i) 更快）
    sink += sb.Length;
}

sw.Stop();
long after = GC.GetTotalMemory(false);
string result = sb.ToString();           // 循环外 ToString，仅一次
Debug.Log($"StringBuilder：总 {after - before} B，耗时 {sw.Elapsed.TotalMilliseconds:F2} ms，sink={sink}");
```

预测参考量级：分配应比 += 的 8.9MB 低约两个数量级，耗时回到毫秒级。跑完和你的错误版（8.9MB/116ms vs 4.5MB/306ms）放进同一张表。

## 三、B4-R：外层重复循环

你上次只把 foreach 执行了 1 次。修正：

```csharp
var list = new List<int>(1000);          // 预容量：别让数组翻倍混进窗口（B2 的教训）
long sink = 0;

GC.Collect();
long before = GC.GetTotalMemory(false);
var sw = Stopwatch.StartNew();

for (int r = 0; r < 10_000; ++r)         // 重复执行 foreach 语句本身
{
    foreach (var i in list) { sink += i; }
}

sw.Stop();
long after = GC.GetTotalMemory(false);
Debug.Log($"总 {after - before} B，每次 {(after - before) / 10_000f:F1} B");
```

两个变体：① 直接声明 `List<int>`；② 声明成 `IEnumerable<int>`（同一个 list）。预期方向：变体一 ≈ 0，变体二每次 foreach 多一个被装箱的 struct enumerator（自己算：多少 B × 1 万次 = 多少 KB）。

## 四、B5-R：四写法重测（样板一个，其余同构）

```csharp
// 变体一：object o = i（预测每次 24B）
long sink = 0;

GC.Collect();                                // 清场
long before = GC.GetTotalMemory(false);      // 快照①
var sw = Stopwatch.StartNew();

for (int i = 0; i < 100_000; ++i)
{
    object o = i;                            // 被测语句：窗口里只有它
    sink += (int)o;
}

sw.Stop();
long after = GC.GetTotalMemory(false);       // 快照②

// 窗口已关闭，现在才允许打印；字节单位 + 算出"每次"
Debug.Log($"object o = i：总 {after - before} B，每次 {(after - before) / 100_000f:F1} B，耗时 {sw.Elapsed.TotalMilliseconds:F2} ms");
```

其余三个变体只换循环体中间两行：

```csharp
string s = $"{i}";        sink += s.Length;   // $ 插值（Unity 下：Format+object 参数）
string s = "x" + i;       sink += s.Length;   // Concat 路线
string s = i.ToString();  sink += s.Length;   // 直接调用
```

要点：① 10 万次（不是 100 万——避免 B1 的"自然 GC 扫垃圾"干扰）② 字节单位（24B 换算成 MB 显示 0，你上轮的"全 0MB"就这么来的）③ 窗口内无 Debug.Log。
交付一张五行表：**四种写法 × 预测每次 B / 实测每次 B / 差异原因**。$ 版比 + 版多出的 ~24B 就是盒子——这个数字到手，装箱课结课。

## 五、A1① / A2② 两句替换原文

- **A1 修正①**，把"栈存值类型，堆存引用类型"换成：
  > 栈存局部变量（值类型的值本身，以及引用类型变量里存的地址），堆存对象本体（实例、数组、盒子）。
- **A2 修正②**，把"arr 本身存的是在堆内存上的引用"换成：
  > arr 变量本身在栈上（它是局部变量），它存着一个引用，指向堆上的数组对象。

## 六、复习材料：B2 的账本（16MB 从哪来）

三个数字分清楚：引用（指针）8B（64 位）、盒子（装箱的 int）24B、`List<object>` 最终引用数组 = 100 万 × 8B = 8MB。

16MB 的来源是**翻倍成长**：List 装满就 new 双倍新数组、拷贝、旧数组整个变垃圾。几何级数：4+8+…+2^20 ≈ 2 × 最终容量 → 累计分配 ≈ 2 × 8MB = 16MB。最终活着的 8MB 是"存活集"，路上的 16MB 是"分配量"——`false` 测量把垃圾也记账，所以看到 16。同一个逻辑预言 `List<int>` ≈ 2 × 4MB = 8MB，你实测 8.4MB ✓ 相互印证。

完整账本：

```text
List<int>     8.4MB  = int 数组翻倍累计（4MB × 2）
List<object> 39.6MB  = 引用数组翻倍累计（8MB × 2）+ 100 万盒子（24MB）≈ 40MB ✓
```

隐藏知识点：`List<T>.Add` 不是零分配（翻倍就是代价），预容量 `new List<T>(n)` 消掉它——W7 Profiler 的 GC Alloc 阶梯就是它。
