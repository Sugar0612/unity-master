## B 新批出的 bug：`yield return null` = 等两帧

你的对照数据：DIY null恢复 **frame=3**，原生 **frame=2**。差异实锤，但你的解释（"原生当前帧就可以处理"）不对——两个版本的"开始"都在 frame 1。死因在你自己的驱动器里，逐帧推演：

```text
帧1: Tick → MoveNext → 打印"开始" → yield null → ProcessYield 设 waitingNextFrame = true
帧2: Tick → flag 为 true → 清掉 → return     ← 这一帧什么都没干，白吃一帧
帧3: Tick → MoveNext → 打印"null恢复"
```

**任务卡需求 2 写的是"yield return null → 下一帧"，你实现了"下下帧"。** 修复两案：

- **a 案（最小）**：删掉那个 `return;`——清完 flag 直接落到 MoveNext。
- **b 案（推荐，也是理解题）**：把 `waitingNextFrame` 字段**整个删掉**，`ProcessYield(null)` 什么都不做。

b 案为什么对：想想 Wait 为什么要存 `waitUntil`——它有状态（deadline）。null 有什么状态？**没有。**"下一帧恢复"本来就是泵的默认行为：这帧 Tick 结束，下帧 Tick 自然 MoveNext。你给一个不需要状态的 yield 发明了状态，这个状态唯一的功能就是多等的那一帧。

**错题 #23：给"无条件等待"发明了条件。** yield null 的正确实现是零代码——想通"协程恢复 = 每帧问一句'条件满足了吗'，而 null 的回答永远是'满足'"，这题就闭环了。
