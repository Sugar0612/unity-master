## B 的致命回归：Tick 重排 = 全死锁

你把 `ProcessYield` 从"MoveNext **之后**处理新产出的 Current"挪到了 Tick **开头**每帧处理 `routine.Current`。推演第一帧：

```text
帧1: Tick → routine.Current = null（还没 MoveNext 过，初始就是 null）
      → ProcessYield(null) → waitingNextFrame = true
      → if (waitingNextFrame) { 清掉; return; }   ← 在这返回了
      → MoveNext 永远执行不到
帧2: Current 还是 null（从没 MoveNext 过）→ 一模一样
帧N: 一模一样 —— 整个驱动器从第一帧死锁，一行日志都不会打印
```

即使第一条 MoveNext 假设跑过了还有第二死法：陈旧 Current 每帧被重新 Process——`waitUntil = Time.time + wait.second` **每帧重置**，deadline 永远滑向未来，Wait 永不到期。

**根因不是逻辑知识，是流程**：你的**二答 Tick 顺序本来就是对的**，三答的"整理"把它弄死了，而演示代码写了却没跑——跑一次，Console 一行没有，10 秒就能发现。**错题 #20：重构已验证代码后必须重跑验证（回归测试的雏形）。数字会告状，Console 也会告状——不跑，它连状都没机会告。**

**修复**：ProcessYield 回到 MoveNext 之后、只处理**当次**产出（即你二答的结构），但保留三答的 Stop 级联/倒序 StopAll/重入防护。改完**必须跑演示并贴 Console 原文**——以后所有演示类交付无 Console 不收卷。

## "快照 vs 活句柄"一段话——讲清楚在问什么

用**你自己的两版代码**对比：

```csharp
// C1（快照）：bool 在调用瞬间被复制，之后外界改什么都与协程无关
Timer.Delay(2f, cb, isGoOn: true);   // 传参那一刻就定死了

// C2（活句柄）：id 是钥匙，到点时刻才去注册表查"我还活着吗"
var h = Timer.Delay(2f, cb);
Timer.Cancel(h);                      // 1.9 秒时取消，依然有效
```

一段话要说清的就是：**C1 的 bool 是调用时刻的值拷贝（W1 副本语义：拷的是当时的值，原值再改不影响拷贝）；C2 的句柄保存 id，协程到点时查注册表——状态是活的，随时可改（W2 scope：控制要认归属）**。用自己的话写 3~5 句，这是 #18 的消灭条件。
