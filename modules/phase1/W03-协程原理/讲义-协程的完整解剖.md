## 第一节 · IEnumerator 契约与编译器状态机

协程的本质：**一个实现了 IEnumerator 接口的对象 + 一个每帧调它 MoveNext() 的调度器**。

```csharp
public interface IEnumerator
{
    bool MoveNext();   // 执行到下一个 yield 或方法结束；返回 false = 协程完了
    object Current { get; }  // 当前 yield 出去的东西（引擎拿它决定"什么时候再叫醒你"）
}
```

你写的协程方法，编译器会翻译成一个**状态机类**（和 W2 的闭包类同一待遇）：

```csharp
// 你写的：
IEnumerator Foo()
{
    Debug.Log("A");
    yield return null;          // 等一帧
    Debug.Log("B");
    yield return new WaitForSeconds(1f);
    Debug.Log("C");
}

// 编译器生成的（近似）：
class <Foo>d__0 : IEnumerator
{
    int <>1__state = -2;        // -2=未启动，0/1=各 yield 点，-1=结束
    object IEnumerator.Current => <>2__current;

    bool IEnumerator.MoveNext()
    {
        switch (<>1__state)
        {
            case 0: goto case 1 ...
            // "A" → state=0, current=null, return true
            // 再被调 MoveNext → 从 state=0 跳进来执行 "B" → state=1, current=W4S, return true
            // 再被调 → "C" → state=-1, return false（协程结束）
        }
    }
}
```

**关键认知**：`yield return` 不是"暂停线程"——是**方法直接返回了**（返回 true + 带着个 Current），引擎记下 Current，下帧（或条件满足时）**再调一次 MoveNext，跳进 switch 接着跑**。所谓"暂停/恢复"= 返回 + 重新进入。

## 第二节 · Unity 的调度器（谁在调 MoveNext？）

`StartCoroutine(Foo())` 的内部：new 出状态机 → **注册进该 MonoBehaviour 的协程列表** → 引擎每帧的更新循环里（Update 阶段之后）逐个调 MoveNext()，**根据上次 Current 决定这次该不该调**：

| Current 是 | 引擎的处理 |
|-----------|-----------|
| `null`（yield return null） | **下一帧**的更新阶段调 MoveNext |
| `WaitForSeconds w` | 记下开始时间，累计时间 ≥ w.duration 才调（**受 Time.timeScale 影响**） |
| `WaitUntil(pred)` | 每帧评估 pred()，true 才调 |
| 另一个 Coroutine | 嵌套：等子协程跑完 |
| 其他 IEnumerator/YieldInstruction | 各有对应规则 |

**笔试错题 P2 的正解现场**（你答"enabled=false 会暂停协程"——错）：
- `enabled = false`：停的是 Update/LateUpdate 等**回调**；协程列表还在引擎手里，**MoveNext 照调，协程继续跑**
- `SetActive(false)` / `Destroy(go)`：协程列表随对象失活/销毁被清，**协程真停**
- `StopAllCoroutines()` / `StopCoroutine(handle)`：手动停

记忆抓手：**协程挂在 GameObject 上，不挂在脚本组件上**。

## 第三节 · async/await 与三者选型

**async/await 在 Unity 主线程恢复**——因为 Unity 安装了 `UnitySynchronizationContext`：await 的"续体"（之后的代码）被 Post 到这个上下文，它在主线程的更新循环里排队执行。所以 await 后碰 Unity API 是安全的（前提：await 的东西不是自己切线程的）。

**三者选型表**：

| | 协程 | Task/async | UniTask |
|---|------|-----------|---------|
| 驱动 | 引擎每帧 MoveNext | 线程池+SynchronizationContext | PlayerLoop 直接注入 |
| 分配 | 每帧装箱 Current、new 状态机 | Task 分配可观 | **零分配** |
| 返回值 | 无（要值靠成员变量绕） | ✓ | ✓ |
| 取消 | StopCoroutine | CancellationToken | CancellationToken/Token 化 |
| 生命周期 | 绑 GameObject | 不绑（对象死了照样跑完） | 可绑 |
| 适用 | 帧时序编排、简单等待 | 独立异步 IO | 高频异步、性能敏感 |

一句话：**帧内时序用协程，异步 IO/带返回值用 async+UniTask**。你简历写了 UniTask——W3 之后要能讲清它"零分配"的原理（复用对象 + 接进 PlayerLoop 不经过 SyncContext 排队）。

## 第四节 · 手写驱动器（任务卡 B 的设计预告）

任务：**不用 MonoBehaviour.StartCoroutine**，自己实现协程的"调度器"那一半（状态机那半编译器免费送你）。核心 API 面：

```csharp
public class CoroutineDriver : MonoBehaviour   // 只用一个空壳 MonoBehaviour 当泵
{
    public Handle Start(IEnumerator routine);  // 注册
    public void Stop(Handle handle);           // 停单个
    public void StopAll();
}

// 支持三种 yield：
yield return null;                    // → 下一帧继续
yield return new Wait(1.5f);          // → 自定义等待类（时间）
yield return subRoutineHandle;        // → 嵌套：等子协程
```

设计要点（自己想，卡住了看提示）：Handle 怎么标识一个协程实例？每帧泵在哪里跑（单例 Update）？Stop 后怎么防止状态机再被调？嵌套时父子生命周期怎么联动（子完父才继续、父死子跟着死）？——这四个问题答清楚，你就把"协程"从 API 变成了你自己的东西。
