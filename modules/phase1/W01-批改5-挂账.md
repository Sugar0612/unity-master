## 四、0B 现象：升级为联合调查（W01 最后一个开放项）

现在有证据链：字符串三变体（预期各 ~300KB）= 0；IEnumerable foreach（预期 ~240KB）= 0；而历史上 151KB/168KB/2.7MB 的读数都正常。**小体量分配在窗口内"净归零"，大体量读数正常**——这不是你写错，是一个真机制，教练也不能 100% 确定成因。两个候选假设：

- **H1（最可疑）：Incremental GC**。你的工程若开了 "Use Incremental GC"（Player 设置，新工程默认开），小量垃圾可能在窗口内被增量式清扫并复用 → 快照②回到快照① → 差值恰好 0。大体量清扫跟不上 → 有残留。
- **H2：测量脚手架结构问题**（比如公共打印/辅助方法在你贴出的代码之外动了内存账）。

**判别实验（差分法，排查课的第一次实战）**：
1. 把两个 foreach 变体（List / IEnumerable，**都用 list.Add 填充**）各跑 **N=100,000 次重复**——量级拉到 2.4MB 级（你有"阈值 ~2.4MB"的先验了）
2. **IEnumerable 读数 − List 读数 = 枚举器装箱的净成本**——两个变体共享一切系统性误差，相减后自动抵消。这就是**差分测量**：测不出绝对值时，测差值
3. A/B 开关：Project Settings → Player → Other Settings → Use Incremental GC 关掉再跑一遍 → 若 0B 变成 ~240KB/300KB，H1 实锤，谜题关闭

## 六、结案（2026-10-27，E2 保活实验）

**结果：1,000,000 次 `arr[r] = ls.GetEnumerator()` → 总 44,412,928 B（44.4B/次），耗时 99.77ms。**

两个结论一次落地：

1. **枚举器装箱实锤**。接口视图的 foreach/GetEnumerator 每次装箱一个 `List<int>.Enumerator`——之前所有"0B"让它隐形，保活后现形。
2. **GetTotalMemory 堆扩张模型实锤**。保活逼迫堆扩张 → 读数出现；此前的 0B = 分配塞进了堆的既有空闲块（仓库有空位就不扩建）。0B 之谜关闭。

**为什么是 44.4B 而不是 24B？盒子大小 = 16B 对象头 + struct 载荷：**

| 装的东西 | 载荷 | 理论盒重 | 实测 |
|---------|------|---------|------|
| `int`（4B） | 4B | 16+4→对齐 24B | 27.2B ✓ |
| `List<int>.Enumerator` | **20B**（8B list 引用 + index/version/current 三个 int） | 16+20→对齐 40B，加堆按块扩张的粒度 | **44.4B ✓** |

推论：**struct 越肥，盒子越贵**——这就是热路径用 `for` 或直接 `List<T>` foreach（struct 枚举器零装箱，见变体一的 0B）的注脚。

**W1 全部挂账清零，正式关账。** 本次调查全程：发现异常 → 可复现 → 假设 → 差分/保活判别实验 → 定案 + 附带新物理（44B 盒子）——这是 H 维度排查方法的第一次完整实战，比任何练习题值钱。

## 七、【修正节】IEnumerable 实验的正确写法（2026-10-27 补）

`IEnumerable<int>` 只承诺"可枚举"，不承诺"可添加"——`Add` 在具体类 `List<int>` 上。所以：**填充走具体类型，测量走接口视图**：

```csharp
List<int> list = new List<int>();
for (int i = 0; i < 1000; ++i) list.Add(i);   // 填充：具体类型，Add 在这
IEnumerable<int> ls = list;                    // 接口视图：只用来 foreach

GC.Collect();
long before = GC.GetTotalMemory(false);
var sw = Stopwatch.StartNew();
for (int r = 0; r < 100_000; ++r)             // 差分实验：10 万次
    foreach (var j in ls) { }
sw.Stop();
long after = GC.GetTotalMemory(false);
```

**这个编译错误本身就是本实验的原理**：声明类型决定了编译器能调用什么，也决定了 foreach 怎么跟对象对话——

```csharp
List<int> a = ...;
foreach (var x in a) { }      // GetEnumerator() 返回 List<int>.Enumerator（struct）
                              // 局部变量直接持有值类型 → 零装箱

IEnumerable<int> b = a;       // 同一个列表！
foreach (var x in b) { }      // GetEnumerator() 签名只承诺 IEnumerator<int>（接口引用）
                              // 具体实现返回的 struct 必须装箱才能进这个引用槽 → 实测 44.4B/次
```

同一个列表、同一份数据，只有**变量声明类型**变了，命运就变了——这就是错题 #1 判定式"值类型进引用槽位就装箱"的原样重演。你撞到的那个编译错误，恰好是这道题的门。
