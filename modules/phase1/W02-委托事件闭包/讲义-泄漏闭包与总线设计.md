## 第一节 · 事件泄漏与"僵尸方法"（对应 A4-R）

### 完整机制（GC 视角）

静态事件（或任何活得比你久的对象上的事件）是一个**根**。你 `+=` 之后，引用链是：

```text
GC根 → 静态字段 OnEvent → 委托（多播链）→ 你的 MonoBehaviour 实例
```

只要这条链在，GC 永远判定"可达"→ **你的实例永远不会被回收**。这就是泄漏的定义。

### 触发时到底发生什么（你答"报空"的纠偏）

场景卸载、GameObject 销毁后，事件再次触发：

1. **托管对象还活着**（正因为泄漏，它没被 GC）→ **方法照常执行**——这就是"僵尸方法"
2. 方法里如果只碰纯 C# 字段（int、List）：**完全正常**，状态还是销毁前的样子（更诡异）
3. 方法里如果碰 Unity 成员（transform.position 等）：**MissingReferenceException**——因为 fake null：托管壳活着，native 对象死了（W4 会展开这个主题）

所以症状是"**僵尸复活**"（逻辑重复执行、报 MRE），不是"报空"。判定"报空"的隐含假设是"对象已经被回收"——而回收恰恰因为泄漏而永远不会发生。

### 正确防御（两条，记死）

```csharp
// 模式一：配对订阅（最常用）
void OnEnable()  { SomeStaticEvent += OnHandler; }   // 命名方法，不是 lambda
void OnDisable() { SomeStaticEvent -= OnHandler; }   // 同一方法引用，减得掉

// 模式二：场景对象的生命周期终点兜底
void OnDestroy() { SomeStaticEvent -= OnHandler; }
```

## 第二节 · 闭包的完整解剖（对应 A5/B2-R）

### 编译器生成了什么（A5 的完整答案）

```csharp
// 你写的：
long sink = 0, x = 10;
Action a = () => sink += x;

// 编译器实际生成的（近似，类名是真实的命名风格）：
class <>c__DisplayClass0
{
    public long sink;                    // 捕获的变量被"提升"为闭包类的字段
    public long x;
    public void <M>b__0() { sink += x; } // lambda 变成了闭包类的方法
}

var dc = new <>c__DisplayClass0();       // ① 堆上创建闭包实例
dc.sink = 0; dc.x = 10;
Action a = new Action(dc.<M>b__0);       // ② 堆上创建委托对象，Target 指向 dc
```

**代价账单**：闭包实例（约 24B+，字段越多越大）+ 委托对象（64 位下约 64B）。这就是为什么捕获型 lambda 不便宜。

### 账单随声明位置变化（B2-R 的预测依据）

- `sink`/`x` 声明在循环**外**（你的代码）：闭包实例**只建一次**（编译器把创建提升到循环外）；循环内每次 `() => ...` 只新建**委托对象** ≈ **64B/次**
- 变量声明在循环**内**：每次迭代 闭包实例 + 委托 两笔都付 ≈ 90~100B/次
- **不捕获的 lambda**：编译器缓存在静态字段里，循环内**零分配**（这就是实验 2 要测出的对比）

### 和 A3 打通

A3 里三个 lambda 打印同一个 3，是因为它们共享**同一个**闭包实例的 i 字段；循环内 `int tmp = i` 之所以能修，是每次迭代**新建一个**闭包实例、各自持有各自的 tmp。同一个机制，两副面孔。

## 第三节 · 强类型事件总线的目标设计（对应 B1-R）

### 你版本的漏洞根源

`EventBus<T, S>` 把"事件身份"（T）和"载荷"（S）拆成两个参数，编译器无法阻止 `EventBus<PlayerDied, int>` 挂上 MonsterDied 的处理器——你的 demo 里就这么发生了。

### 目标设计：事件 struct 本身就是载荷（单泛型参数）

```csharp
public static class EventBus<T> where T : struct
{
    private static event Action<T>? OnEvent;     // 静态泛型路由：每个T一份

    public static void Subscribe(Action<T> handler)   => OnEvent += handler;
    public static void Unsubscribe(Action<T> handler) => OnEvent -= handler;
    public static void Publish(in T evt)              => OnEvent?.Invoke(evt);
}

// 用法：
struct PlayerDied { public int Id; }
struct MonsterDied { public int Id; }

void OnPlayerDied(PlayerDied evt) => Debug.Log($"玩家{evt.Id}阵亡");

EventBus<PlayerDied>.Subscribe(OnPlayerDied);
EventBus<PlayerDied>.Publish(new PlayerDied { Id = 3 });

// MonsterDied 的处理器想订 PlayerDied？
// EventBus<PlayerDied>.Subscribe(OnMonsterDied);  // ← 编译错误：Action<PlayerDied> ≠ Action<MonsterDied>
```

**类型安全在这一刻兑现**：订错事件从"运行期逻辑 bug"变成"编译期红线"。你的静态泛型路由思路保留（这是对的），只是把两个参数合成一个。

### 预测题的答案

你的设计**没有字典**（静态泛型路由本身免了字典）——这可以作为满分答案。若用字典：`Dictionary<Type, ...>` 的键 `typeof(T)` 返回的 Type 对象是**引用类型**且运行时缓存同一个实例，作键**不装箱**——装箱只发生在值类型进引用槽位（W1 判定式第 N 次复用）。

### 与你框架的对照（C-R 素材）

你的 Essentials `EventBus<EventType> where EventType : IEventBus` 和目标设计**结构相同**，多了 marker interface 约束：事件必须显式 `: IEventBus` 声明"我是事件"——意图明确、防止随手拿个 struct 当事件。三条差异、一条保留、一条改进现在应该好写了。

## 第四节 · B3 的修法示范（不是唯一答案，你要做判断）

`ControlBase.cs` 两个 bug 的修复方向，**两种方案选一个并说明理由**：

**方案 A：命名方法配对订阅**（讲义第一节的模式一）

```csharp
private void OnEnable()
{
    onClickEnter  += OnClickEnterHandler;    // 命名方法
    onHoverEnter  += OnHoverEnterHandler;
    onHoverExit   += OnHoverExitHandler;
}
private void OnDisable()
{
    onClickEnter  -= OnClickEnterHandler;    // 同一方法引用，减得掉
    onHoverEnter  -= OnHoverEnterHandler;
    onHoverExit   -= OnHoverExitHandler;
}
private void OnClickEnterHandler()  => RaiseTrigger(InteractionTrigger.Selected);
private void OnHoverEnterHandler()  => RaiseTrigger(InteractionTrigger.HoverEnter);
private void OnHoverExitHandler()   => RaiseTrigger(InteractionTrigger.HoverExit);
private void OnDestroy()            => RaiseTrigger(InteractionTrigger.ObjectDestroy); // 修正触发器
```

**方案 B：根本不订阅——直接 override**。文件底部的注释示例揭示了 `Interactable` 本来就有 `OnClickEnter/OnHoverEnter/OnHoverExit` 虚方法，ControlBase 绕道"订阅自己的事件再转发"纯属多余：

```csharp
protected override void OnClickEnter()  => RaiseTrigger(InteractionTrigger.Selected);
protected override void OnHoverEnter()  => RaiseTrigger(InteractionTrigger.HoverEnter);
protected override void OnHoverExit()   => RaiseTrigger(InteractionTrigger.HoverExit);
private   void OnDestroy()              => RaiseTrigger(InteractionTrigger.ObjectDestroy);
```

无订阅就无退订，泄漏在结构上不可能发生。两个方案的取舍（子类是否还需要 override 的自由、转发链长度）由你判断并写在答卷里。

### 为什么匿名 lambda 连 -= 都做不到（B3 必答）

`onClickEnter += () => ...` 和 `onClickEnter -= () => ...` 里的两个 lambda，编译器各生成**一个新委托对象**（必要时还各建一个闭包实例）。`-=` 按"方法+目标"相等性移除——**新造的对象永远不等于已存的对象**，所以减不掉。这就是"匿名订阅必须配命名退订"或"干脆 override"的原理，也是你 SNNU 框架那个 bug 的病理。
