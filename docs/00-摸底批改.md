## Part A · C# 与运行时

### A1（1.5/3）装箱与堆分配
- ① `object o = score` 装箱 ✓ 对。
- ② string 拼接：**有分配，但不是装箱**。装箱特指"值类型被包装成对象"，string 拼接是新建字符串对象（普通分配）。另外新编译器下 `"Score: " + score` 会编译成 `string.Concat("Score: ", score.ToString())`——ToString 本身先分配一个字符串，拼接再分配一个，共两处分配。
- ③ `Debug.Log(s)`：**分配很大，你答"不产生"是错的**。即使传现成的 string，内部要抓调用栈、构造日志条目——它是隐藏的分配大户，生产代码要条件编译屏蔽。
- ④ `score.ToString()`：**有分配（字符串本身），但不是装箱**。编译器用 constrained callvirt 直接在值类型上调用虚方法，不经过对象包装。
- **核心纠偏**：把"产生堆内存"和"装箱"划等号是概念混淆。装箱=值类型→对象包装这一种特定分配。

### A2（1/3）闭包
- 正确答案：一次点击输出 **3、3、3**（三行）。`for` 的循环变量是**同一个变量**，三个 lambda 捕获的都是它；循环结束时 i=3，三个监听都打印 3。你答 "222" 错，且推理"i 是临时变量不会被持久化"方向反了——恰恰因为**被捕获的变量被持久化**（提升为闭包类的字段）才有这个陷阱。
- **你的修复 2 ✓（循环内 int tmp = i）是标准答案。修复 1 ✗ 无效**——tmp 声明在循环外，三个 lambda 捕获的还是同一个 tmp，行为完全不变。这个错误本身暴露了你对"捕获的是变量（槽位），不是值"这一点没有模型。

### A3（1.5/3）协程原理
- "状态机"方向 ✓，但没说到关键机制：编译器把协程方法转成 **IEnumerator 状态机类**，引擎把协程注册到 MonoBehaviour 的更新列表，**每帧在 Update 之后调一次 MoveNext()**，恢复到上个 yield 处执行到下一个 yield。协程不是线程，是"每帧被叫醒一次的迭代器"。
- `enabled = false`：**协程继续跑**（停的是 Update/LateUpdate 等回调）——你答错了。`SetActive(false)`：停 ✓（Destroy 同理）。
- async/await 主线程恢复：**✓ 答对了**（UnitySynchronizationContext 把续体投递回主线程）。
- 选型方法论缺位：协程=帧内时序编排、与 GameObject 生命周期绑定；async=独立于场景对象的异步 IO 与组合取消；UniTask=零分配版的 await。

### A4（1/3）假 null
- `go == null` 是 **true**，你答 false 错。Unity 重载了 `==`：Destroy 后 native 对象已销毁，托管包装被标记为 fake null，`==` 检查的是 **native 侧存活**而不是托管引用。你的解释（"垃圾到一定程度才 GC、变成未激活放堆里"）是一套错误模型——托管对象确实还在等 GC，但判空结果在 Destroy 当帧就变 true，和 GC 完全无关。
- Destroy=帧尾异步销毁（运行时唯一选择）；DestroyImmediate=立即同步（只该在 Editor 代码用）。你的"软/强制"描述碰到了边，没说清使用场景。
- `go?.name` 与 `if (go != null)`：**行为不同**。`?.` 不能重载，走真实引用判空——fake null 的对象引用非空，会通过检查，然后 `.name` 抛 MissingReferenceException。你在 SNNU 框架里写过 fake-null 的注释（结论背过），但模型没建立，所以这题答"没区别"。

## Part B · 核心机制与网络

### B1（1/3）生命周期
- 你的顺序：Awake→OnEnable→Start→**协程恢复→Update→FixedUpdate**→LateUpdate→OnDestroy。
- 正确：Awake→OnEnable→Start→ 每帧循环【**FixedUpdate（0~N 次）→ Update → yield null 协程恢复 → LateUpdate**】→渲染→…→OnDestroy。你把协程恢复点放到 Update 前、FixedUpdate 放到 Update 后，**两处都反了**。
- 未作答的子题：FixedUpdate 由 fixedDeltaTime 累积器驱动——一帧内可以 0 次（帧耗时短于 fixedDelta）也可以多次（追帧/卡顿后追进度），这是物理和渲染解耦的关键。

### B2（1/3）LateUpdate 与抖动
- 诚实承认不清楚。正解：多个脚本的 **Update 执行顺序不确定**，角色移动和相机跟随都写在 Update 时，相机可能取到移动前的旧位置（取决于谁先跑）→抖动。LateUpdate 保证所有 Update 完成后执行 → 相机永远拿当帧最新位置。解决不了的：物理驱动的移动抖动（要用 Rigidbody 插值）、动画时机问题。

### B3（1/3）Instantiate 贵在哪
- "drawcall 和 gc" 是表象堆砌。底层原因至少有：①native 侧对象创建+**反序列化**（逐字段读序列化数据重建对象图）；②托管 wrapper 分配 → GC 压力；③场景层级注册（transform dirty 传播通知）；④材质/shader 变体首次 warmup；⑤大 prefab 的内存分配与碎片化。对象池治的是 ①②⑤。

### B4（1.5/3）SyncVar 原理
- 机制"不知道"——正解：Mirror 的 **Weaver 在编译后改写 IL**，为 NetworkBehaviour 子类的每个 SyncVar 实例字段生成脏标记+序列化代码，同步以"对象实例"为单位进行。
- static 不同步：**结论对**，且"属于类不属于对象"的直觉方向对——正因为 Weaver 织入的是实例字段的序列化路径，static 字段根本不在覆盖范围。你是靠"Mirror 不允许"这条规则答对的，原理层空白。
- 客户端赋值 SyncVar：本地值会变但不会广播，且会在下次服务器同步时被覆盖回去。你答"无权修改所以无效"结论接近，但"权限"是规则描述不是机制——机制是只有服务器端的织入代码才发送 delta。

### B5（1/3）网络竞态
- **结论对（读不到新值），归因全错**。不是权限问题——是**时序**问题：Command 要经过 本机→网络→服务器→Rpc→网络→本机 才能更新 SyncVar，往返几十毫秒；onClick 同步代码在 Command 刚发出去几微秒后就执行了。就算权限完全放开你也读不到。
- 正确写法：把后续逻辑放进 **SyncVar 的 hook 回调**（值变化自然触发），或用 **TargetRpc** 回调发起者。"在 Command 里修改 SyncVar"答非所问。
- **这是本次笔试最有代表性的失分**：规则背了不少（权限、服务器权威），但没有"网络往返是异步的"这个心智模型——和你 RSHE 项目里 `Transporter.cs:70-83` 的真实 bug 一模一样。
