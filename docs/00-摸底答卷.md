## Part C · 性能优化

**C1**：DrawCall是Cpu往GPU传递的一个单位，SetPass Call不知道，合批就是把相同的Mesh或者Shader或者Material一起批处理，减少DrawCall的次数。
动态合批：应该是相同Mesh，相同Material，相同Shader的一种批处理方式，但是好像面数有限制只适用于700面以下的。适用于URP
静态合批：是不同Mesh，相同Shader批处理方式，适合场景中的建筑物模型。适用于BRP、URP。
SRP Batcher：是可以不同Material相同Shader的一种批处理方式。适用于URP。
GPU Instancing：适用于相同Mesh，相同Materail，比如场景中大量的植物花盆，子弹等。
UGUI 里改一个 Text 的文本，为什么可能引起整个 Canvas 的大开销？因为Text改变之后都会进行一次Canvas ReBuild，相当于有Text的这个Canvas就要重新绘画一次，会产生很多的DarwCall，所以开销可能会很大。  

**C2**：需要链接真机打开Profiler，然后主要就是看掉帧的那一帧的GC Alloc和DarwCall，如果是GC Alloc那就去看代码中哪个地方造成了GC压力，可以关注以下Update函数中是否有不合理的装箱操作导致了卡顿。然后就是看CPU频率是不是突然升高，如果是那就看场景中是不是没有用对象池在频繁的生成和销毁。DarwCall一般都是持续卡顿，应该不会是这种突然某一帧卡顿，所以大概率在CPU和GC Alloc中关注。  

**C3**：Unity 的 GC（Mono/Boehm）是"非分代、非压缩"的——这句话意味着这句话意味着GC的触发是某一帧突然发生的，GC垃圾也没有进行过压缩，数量会很庞大，对帧率是非常不友好的影响。减少GC的手段：
1. 不要在Update中定义引用类型，因为引用类型会产生不必要的GC Alloc。
2. string拼接要用StringBuilder
3. 尽量避免重复的装箱操作
4. 用UniTask替换协程
5.目前想不出来了
`foreach (var x in list)`（list 是 `List<int>`）int是值类型应该是没有有 GC 分配的，IEnumerable<int>相当于是在一个引用类型中装箱了一个值类型是由GC分配的。

## Part H · 综合排查

**H1**：首先就是用数据线连接主机打开unity profiler，然后开始运行真机，主要是看GPU频率和CPU频率，如果是GPU频率高，那就说过DarwCall大概率有问题，需要去排查项目中是否静态批处理了，是否进行了合理的SRP Batcher，小而多的物体是否进行了GPU Instaning，还有就是实施光照也要检查，场景中的实施光照是否太多了，如果是那就要进行灯光烘培，只留一个实时的方向光，再看场景中LOD是否合理，尤其是摄像头在某个角度要渲染多个物体更容易让DrawCall升高，所以要对场景中的物体比如树木，石头都要LOD化。如果GPU没问题，看看CPU频率，如果CPU频率高，那说明代码中有不合理的内存开销，就要检查项目中关于生成和销毁的代码是否频繁调用，看每一帧的堆栈哪个函数占用的最多的资源，评估是否合理。如果CPU和GPU频率都没问题，那就看电池使用情况，看后台是否有其他没用的PID占用。
